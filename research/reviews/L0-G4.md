## Blocking defects
- platform · 1 (honesty) · `description` ("The hosted Huly service is being shut down, according to a notice in the README,
  which says self-hosted installs are not affected") and `limits[1]` ("The hosted Huly service is being discontinued").
  The README of hcengineering/platform today says "Hosted Huly has shut down … The hosted platform is no longer available",
  and also "This repository is frozen and is no longer actively maintained. Development continues in
  Platform-Collective/platform" (commit "Frozen maintenance", 2026-09-25). The text is stale on the shutdown and silent on
  the frozen repo, which is the fact a reader most needs. research/data-issues/L0-p06.md was wrong on both points
  (it read an older README with "expected on July 20").
  Fix: say the hosted service has shut down; say the hcengineering repo is frozen (it still gets occasional fixes) and that
  development continues in an independent community fork, Platform-Collective/platform, which is young and small. Add a
  limit along the lines of "Upstream repository frozen since September 2026; future development depends on a community
  fork". Re-source both lines to https://github.com/hcengineering/platform and https://github.com/Platform-Collective/platform.
  Blocking: yes.
- asana · 1 (honesty) · `alternativeNotes.platform`: "its hosted service is being discontinued". Same stale fact.
  Fix: "Its hosted service has shut down and the original repository is frozen; development continues in a community fork."
  Controller: consider whether Huly should stay in Asana's `alternatives` at all while the upstream is frozen. Blocking: yes.
- asana · 1 · `alternativesIntro`: "You lose the mobile apps, real-time editing and the notifications that make a team
  actually use the tool." This is lifted from `whatYouLose` (which is about a personal build) and applied to Leantime.
  Leantime ships a Notifications module (app/Domain/Notifications in Leantime/leantime); no source supports the claim.
  Fix: drop "the notifications…" or replace with something sourced, e.g. "You lose native mobile apps, real-time
  co-editing and Asana's integration catalogue." Blocking: yes.
- osticket · 1 · `limits[3]`: "The last commit in our data is from June 2026, a slower pace than most projects here".
  Dates in prose are a defect (the table shows the live last commit). Fix: delete this limit or replace it with a sourced
  functional gap (e.g. no REST API for ticket creation beyond the legacy key-based endpoint, if sourced). Blocking: yes.
- threaduler · 1 · `description` ("The repository has few stars and its last commit in our data is from December 2025")
  and `limits[4]` ("…the last commit in our data is from December 2025"). Dates in prose. Fix: keep the judgement without
  the date, e.g. "Development looks inactive and the README is mostly the default template, so treat it as a starting
  point." Blocking: yes.
- trypost · 1 · `description` ("The project started in January 2026, so it is young compared with Hootsuite") and
  `limits[0]` ("the repository was created in 2026"). Dates in prose. Fix: "A young project with a fast-changing feature
  set" without the date (the table shows creation and last commit). Blocking: yes.
- hootsuite · 1 · `alternativeNotes.trypost`: "It is a young project created in 2026". Same rule. Fix: "It is a young
  project, and you set up each network's API access yourself." Blocking: yes.
- trypost · 4 · `description`: "A composer writes a post once and adapts it per network, with a live preview." vs README
  "Composer that writes once and adapts per network, with a live preview"; and "Members can send posts for approval, and
  admins approve or reject them." vs README "members who need a review send posts for approval, and admins approve or
  reject in one click". Near-verbatim. "queues that fill the next free slot" also mirrors "New posts take the next free slot".
  Fix: rewrite these three sentences in your own structure (e.g. "You write one post and edit a version for each network,
  checking a preview as you go. Each channel has posting times; new posts drop into the next open one. A review step lets
  admins accept or send back a member's post."). Blocking: yes.
- stirling-pdf · 4 · `description` first sentence: "Stirling PDF is a PDF platform you can run as a desktop app, in the
  browser, or on your own server with a private API." vs README "Run it as a personal desktop app, in the browser, or
  deploy it on your own servers with a private API." Near-verbatim. Fix: restructure, e.g. "Stirling PDF ships three ways:
  a desktop program, a web interface and a server that exposes an API on your own network." Blocking: yes.

## Notes (non-blocking)
- threaduler · `tagline`, `strengths[3]`, `bestFor`, and hootsuite `alternativeNotes.threaduler` state Bluesky support as
  fact. The README header claims it, but its roadmap still lists "add bsky integration" as open and setup asks only for an
  X key (the writer flagged this in L0-p08). Fix: "X, with Bluesky support claimed but unconfirmed" or drop Bluesky.
- socioboard · `description` ("does not state a licence in its README, so check the licence file") and `limits[3]`
  ("lacks a clear licence statement"). The repo's LICENSE file is GPL-3.0. Literally true about the README, but misleading.
  Fix: "The LICENSE file is GPL-3.0; the README itself does not mention it." Data pass: `license` should be GPL-3.0
  (L0-p07 says none).
- "our data" in public prose: uvdesk `description` ("no hosted service is listed in our data"), frappe-helpdesk
  `description` ("our data lists no separate hosted offer"), osticket and threaduler (above). Internal wording on a public
  page, and in uvdesk/frappe it describes a data field already known to be unreliable. Fix: state the fact ("The project
  sells no hosted plan of its own" / "Frappe Cloud hosts it as one of many Frappe apps") or drop it.
- Generic limits: zammad `limits[3]` ("Hosting, backups and updates are on you…"), chatwoot `limits[3]`, postiz-app
  `limits[3]`. True of every self-hosted project. Each file has other specific limits, so point 2 passes; replace these with
  product-specific ones when the batch comes back.
- operately · `description`: "let scripts and AI agents create goals, update projects and post check-ins" echoes the README
  "AI agents can create goals, update projects, and post check-ins". Feature verbs, close to the line; rephrase.
- pdfarranger · `limits[3]` "No macOS package is listed in the README downloads section": true, but the README links
  macOS.md for macOS. Fix: "macOS has no packaged build; you follow the macOS.md source instructions."
- smartsheet · FAQ 6 answers with Redmine and Leantime but not OpenProject, the named winner (which also has per-project
  roles). Consider leading with OpenProject for consistency with the intro.
- research/data-issues/L0-p06.md (platform) is out of date and should be corrected: the README now says hosted Huly has
  shut down and the repo is frozen; the canonical development repo is Platform-Collective/platform (a fork, 89 stars).
  The `repo` field and the stars shown (27,935, from the frozen repo) need the data pass.
- Tool sources: `alternativeNotes.*` entries point to the project i18n files instead of per-claim URLs, and `faq[5]` cites
  "data/i18n/en/projects", which is not a URL. Acceptable because the project files carry the sources, but the tool-only
  claims (Smartsheet free contributors, Acrobat Sign audit trail, Hootsuite's approved apps) should have their own lines.
- chatwoot · `description` has one 42-word sentence (deploy options). Average is fine; split it.
- Brief conflict for the controller: review-gate grid point 1 says licences in prose are a defect, while write-project §5
  tells writers to take licence facts from data. I did not fail licence mentions that match `data/` and the repo. Please
  settle the rule before the next batch.
